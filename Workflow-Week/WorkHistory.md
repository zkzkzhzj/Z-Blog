이전 회사에서 스프링 프로젝트를 할 때 패키지 구조는 비즈니스 로직별 구조를 가졌었는데

비즈니스 로직별 구조로 갔을 때 장점은 기능별로 찾아가기는 정말 쉬웠다.

다만, 그 기능별로 구분된 패키지 내부에서 특정 도메인의 로직을 찾기에는 불편한 점이 생겨 추후에 도메인별 구분도 추가하여 비즈니스 -> 도메인 구조를 가져갔었다.

지금 단순히 블로그 라는 주제 하나로 간다면 비즈니스 로직 구조가 단순하고 쉬울 것 같지만

추후에 내가 하고싶은 기능들을 마음껏 넣을 예정이기 때문에 도메인 -> 비즈니스 로직 구조로 가져가야겠다.

비즈니스 -> 도메인보다는 개인적으로 도메인 -> 비즈니스 패키지 구조가 더 편리하다고 생각되어 해당 구조로 잡는다.

이번 주말 목표는 아래로 잡자

1. weekly-report.md 파일 관리할 수 있도록 템플릿 정의 및 추가
2. 현재 git push 를 일별로 진행하고 있는데 좋지 않은 것 같다.. commit 로그가 지저분해질것 같으므로 branch 전략을 주말에 정하자.
    1. 이전에 issue 를 활용하고 했던 기억이 있는 데 issue 보다는 우선적으로 브랜치를 구분지어가지고 커밋 로그를 좀더 깔끔하게 잡기로 하자

    1. 원래 목표는 공식문서를 보고 컬럼의 annotation 속성을 하나하나 찾아가며 지정하고 싶었는데 시간이 너무 들어가는 것 같더라..
